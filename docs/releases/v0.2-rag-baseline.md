# `v0.2-rag-baseline` — first end-to-end RAG over the corpus

**Date:** 2026-06-23

## Scope

A naive but complete, fully local, open-source RAG pipeline over the
`v0.1-corpus` (7,004 abstracts): embed → vector search → grounded generation.
First end-to-end answer (question in, PMID-cited answer out). No eval harness,
no fine-tuning, no agent at this tag — those are later milestones. The point of
this tag is a **baseline to measure against**, not a tuned system.

## Architecture

```
question
  │  bge-base-en-v1.5 (transformers, GPU)        ← embedding
  ▼
qdrant local mode (data/qdrant/)                 ← vector store, cosine
  │  top-k = 5
  ▼
Qwen2.5-3B-Instruct, 4-bit NF4 (transformers)    ← generation
  ▼
grounded answer + PMID citations
```

All models run locally on an RTX 3060 Laptop (6 GB VRAM). Combined footprint at
query time ~2.5 GB (bge ~0.4 GB + 4-bit Qwen ~2.1 GB).

## Key decisions

### Generation: Qwen2.5-3B-Instruct, 4-bit, local — never an API model

The project's generator is a **local open-source model** (per `architecture.md`:
"generation (LoRA-tuned 3B)"), tuned at `v0.5`; at `v0.2` it's the *un-tuned*
base, so `v0.5` can measure the fine-tuning lift against this baseline.

- **Qwen2.5-3B-Instruct** over Llama-3.2-3B: Apache-2.0 and ungated (no license
  click-through / token), top-tier 3B quality, clean LoRA path for `v0.5`.
  Swapping models is a one-line change; Llama is a natural A/B at `v0.3`.
- **4-bit NF4 quantization** (`bitsandbytes`): a 3B model is ~6 GB at fp16 and
  will not fit 6 GB VRAM; 4-bit shrinks it to ~2 GB with a small, well-
  characterised quality cost. Also the on-ramp to QLoRA at `v0.5`. Runs fine on
  Windows with current `bitsandbytes`.
- **Greedy decoding** (`do_sample=False`): deterministic answers for a
  reproducible baseline.

### Embedding: bge-base-en-v1.5 (general), via `transformers`

- A strong **general-purpose** 768-dim retriever, used off-the-shelf. A
  domain-specific embedder (PubMedBERT / MedCPT) is a deferred **`v0.3`
  comparison** — measure whether biomedical embeddings help rather than assume.
- Run through **`transformers` directly** (CLS pooling + L2 normalise), **not
  `sentence-transformers`**, which segfaulted on this Anaconda + pip-torch setup
  (exit 139 during model load). Going one layer down to the already-proven
  `transformers` path fixed it and dropped a heavy dependency.
- bge query/document asymmetry honoured: queries get the instruction prefix,
  documents do not.

### Retrieval: qdrant, local mode

- qdrant per `architecture.md`. Run in **local on-disk mode** (`data/qdrant/`),
  no server/Docker — appropriate for a single-machine baseline.
- Cosine distance; vectors L2-normalised at embed time.

### top-k = 5 — an untuned default

Chosen by hand, not measured. `k` is a real RAG hyperparameter (small k = less
noise but may miss; large k = better recall but more off-topic context).
Tuning `k` against retrieval metrics is a **`v0.3`** job. (It already bit us —
see findings.)

## Findings (qualitative — eyeball, not measured)

- **Retrieval discriminates sub-topics within the corpus.** Distinct queries
  (nutrition / CT imaging / EMG methods) return distinct, sub-topic-appropriate
  abstracts — not the same generic reviews. This is the meaningful check given
  that *every* document is "about sarcopenia"; mere on-topic retrieval would
  prove nothing.
- **Absolute cosine is not a quality threshold.** Scores compress into a narrow
  high band (top hits ~0.78–0.86; rank-500 still ~0.63), and the ceiling varies
  by query. Signal is in *ranking/gap*, not the absolute value.
- **Faithfulness is not guaranteed (known failure logged).** For "handgrip
  strength cutoff values…", k=5 pulled in a *knee-extension* paper
  (PMID 32470897) because "cut-off + strength + sarcopenia" dominates the
  embedding; the model then cited its knee-extension cutoffs as handgrip values.
  A claim attributed to a non-supporting source — exactly what a `v0.3`
  faithfulness metric must catch. See `docs/eval_query_candidates.md`.
- **Speed:** ~9 tok/s generation on the 3060 (a ~300-token answer ≈ 16 s).
  Acceptable for a baseline; optimisable later.

## Eval delta vs previous tag

n/a quantitatively — **this is the baseline**. No metrics yet by design; `v0.3`
builds the harness (recall@k, MRR, nDCG for retrieval; faithfulness/groundedness
for generation) and produces the first numbers. Findings above are qualitative.

## Known issues / debt

- Faithfulness failures (knee-extension/handgrip conflation) — unmeasured until
  `v0.3`.
- `k=5` untuned; no chunking (abstracts indexed whole — fine at this length).
- `lxml` and `datasets` remain pinned but unused (from `v0.1`); `ml` extra adds
  the real GPU stack. Candidate cleanup.
- Index rebuild re-embeds all 7,004 each run (~2.3 min); no embedding cache yet.
