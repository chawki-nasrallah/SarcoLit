# `v0.4-rag-improved` — measured improvements (none adopted) + bottleneck located

**Date:** 2026-07-11

## Scope

An **eval-driven** milestone: three plausible RAG improvements were built and
rigorously measured against the `v0.3` baseline. **None beat it, so none shipped**
— and that is the result. The milestone's value is what the measurement
*revealed*: retrieval is already strong, and the real bottleneck is the 3B
model's **attribution capability**, which prompting cannot fix — pointing
directly at `v0.5` (fine-tuning). It also delivers the **gold expert eval set**.

This is the eval harness earning its keep: it stopped three changes that
intuitively "should" help but measurably don't.

## Improvements tested

### 1. Cross-encoder reranker — rejected

Two-stage retrieve-and-rerank (bge top-30 → `bge-reranker-base` → top-5).
Measured on the synthetic set (n=150): it **hurt** across the board.

| | recall@1 | recall@5 | MRR | nDCG@5 |
|---|---|---|---|---|
| baseline (bge) | 0.700 | 0.907 | 0.784 | 0.813 |
| + reranker | 0.667 | 0.893 | 0.761 | 0.790 |

Why: the synthetic queries are generated *from* their source abstracts, so bge
already ranks the source near rank 1 (near-ceiling). Reranking just adds churn
and demotes some rank-1 sources. Rerankers help when base retrieval is weak or
queries are hard — not here.

### 2. Hybrid search (dense bge + sparse BM25, RRF fusion) — rejected

On the synthetic set it looked like a marginal win (recall@10 0.927→0.953). But
the **gold set reversed the conclusion** — on realistic, expert-labelled queries
with a fair multi-method pool, bge beats hybrid on **every** metric:

| gold (n=14) | MRR | nDCG@1 | nDCG@5 | recall@10 |
|---|---|---|---|---|
| bge | **1.000** | **1.000** | **0.921** | **0.590** |
| hybrid | 0.929 | 0.857 | 0.832 | 0.459 |

(Note: low absolute recall@k is the *multi-relevant denominator* — ~14 relevant
docs per gold query — not poor retrieval; MRR=1.0 and nDCG@1=1.0 mean bge's top
result is *always* relevant. nDCG is the metric to trust with multi-relevant
queries.) Why hybrid loses: natural-language questions are bge's strength; BM25
promotes keyword-sharing but less-relevant docs, diluting the ranking. The
synthetic "win" was an artifact of easier, keyword-literal synthetic questions.
Also regressed faithfulness on synthetic (0.80→0.70).

### 3. Faithfulness prompt engineering — rejected (3 variants, all hurt)

Three progressively stricter grounding/verification prompts, A/B-tested for
faithfulness (synthetic, n=30, bge):

| prompt | faithful rate | mean score |
|---|---|---|
| baseline (simplest) | **0.800** | **0.902** |
| + strict source/anti-overstatement rules | 0.700 | 0.883 |
| + self-verify-each-claim rule | 0.667 | 0.882 |

**Monotonically worse with more rules.** Misattribution is a **capability limit
of the 3B model** (it can't reliably track which source states which specific
fact) — no instruction adds that skill, and extra rules *degrade* a small model.
Reverted to the simplest baseline prompt.

## Gold expert eval set (delivered)

14 realistic queries, hand-labelled by the domain expert, over a **fair
multi-method pool** (bge ∪ BM25) — which fixes the self-pooling bias that
deferred the gold set at `v0.3` (only possible now that a second retriever
exists). Committed to `evals/gold_queries.jsonl`; labelling tool in
`eval/label_gold.py`.

## Eval delta vs `v0.3`

**Shipped config unchanged** (bge, baseline prompt — still the best). No metric
moved because nothing was adopted. The delta is *knowledge*: retrieval confirmed
strong; the faithfulness bottleneck localised to model capability. New realistic
retrieval baseline on the gold set: MRR 1.0, nDCG@5 0.92 (bge).

## Known issues / debt

- No perf improvement shipped (by design — nothing beat baseline).
- Faithfulness comparisons are n=30 (wide error bars); the *pattern* (all prompt
  variants worse) is the robust signal.
- **Abstention threshold** (OOD-refusal short-circuit) and a **chain-of-
  verification pass** were scoped but not built — candidate future levers.
- `rerank`/`hybrid` kept in-repo as documented negative results, not wired into
  the default pipeline.

## Next milestone

`v0.5-finetune` — LoRA/QLoRA fine-tune Qwen to fix the **located** bottleneck
(attribution / faithfulness), measured against this baseline. This is where the
un-tuned `v0.2` baseline and the `v0.3` harness finally pay off: a *quantified*
lift from fine-tuning, targeting a problem we've proven prompting can't solve.
